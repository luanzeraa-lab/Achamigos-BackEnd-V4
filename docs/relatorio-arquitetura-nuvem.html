Da API local para uma nuvem operável.

Leitura arquitetural do backend Achamigos e proposta de fluxo para Oracle Cloud, com MongoDB Atlas, frontend separado e acesso público somente por HTTPS.

Direção recomendada

OCI Container Instances em sub-rede privada, atrás de Load Balancer público, com NAT Gateway para as integrações externas.

O que já existe

O código já contém os principais caminhos funcionais, mas alguns contratos ainda precisam ser endurecidos antes da publicação.

Aplicação

Fluxo principal

Express monta as rotas sob /api, conecta ao MongoDB via Mongoose e publica Swagger em /docs.

  • Animais e eventos usam Cloudinary para imagens.
  • GenAI chama o Google Gemini pelo backend.
  • Logs de aplicação são enviados ao Logtail.
Desenvolvimento

Compose local

O Docker Compose sobe frontend, backend e MongoDB em uma bridge local.

  • Não deve ser copiado literalmente para produção.
  • A porta 27017 não deve ser pública.
  • O disco local não é armazenamento persistente de produção.

Antes do go-live

Os itens abaixo são bloqueadores ou riscos importantes para uma API pública.

Prioridade alta

Segurança de acesso

  • API key está desativada em api.ts.
  • JWT existe, mas não é emitido no login nem aplicado às rotas.
  • CORS está aberto para qualquer origem.
  • Token Logtail e API key aparecem no Compose.
Prioridade alta

Dados e observabilidade

  • Upload de usuário grava no disco efêmero do container.
  • Logger envia headers e bodies completos, podendo capturar credenciais.
  • Não há readiness real para confirmar conexão com MongoDB.
  • GenAI não tem limite de prompt, rate limit ou controle de custo.
Prioridade média

Reprodutibilidade

  • tsx é executado no build, mas não está declarado diretamente.
  • Docker usa Node 20; CI documenta Node 22.
  • O build regenera artefatos versionados em dist/.
Prioridade média

Operação

  • Não há health check de container nem graceful shutdown.
  • Listagens não têm paginação.
  • Uploads não têm limite de tamanho ou validação de tipo.
  • Swagger e README divergem de algumas rotas reais.

Roteiro de implantação

Uma sequência curta para reduzir risco sem exigir Kubernetes de início.

Fundação OCI

VCN, sub-redes pública/privada, NSGs, Load Balancer, NAT Gateway e DNS.

Dados e segredos

Atlas com TLS, backup e allowlist; segredos em Vault/Secret Manager, nunca no Compose.

Aplicação

Imagem imutável, health check, upload persistente e autenticação efetiva antes de abrir o endpoint.

Operação

Logs sem dados sensíveis, métricas, alertas, rollback e teste de restauração.

Decisões para fechar o desenho executivo

  1. Usar OCI Container Instances como primeira plataforma ou iniciar diretamente com OKE?
  2. Manter acesso ao Atlas por IP fixo do NAT Gateway ou avaliar conectividade privada?
  3. Migrar imagens de usuários para Cloudinary ou OCI Object Storage?
  4. Qual mecanismo será oficial: JWT, API key ou combinação dos dois?
